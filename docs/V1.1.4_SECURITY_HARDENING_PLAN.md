# v1.1.4 Security Hardening Plan

Status: development only. This document does not announce or authorize a v1.1.4 release.

## Current baseline findings

- Release build previously had `isMinifyEnabled = false`; R8 shrinking/obfuscation is now enabled on `security/v1.1.4-hardening`.
- Release signing is configured around the existing permanent certificate. Preserve it for all future upgrades.
- The app uses private SharedPreferences for protection state and authentication throttling. This data is currently not encrypted at rest by an app-managed encryption layer.
- The Android manifest disables backup, disables cleartext traffic, and declares no CAMERA permission. The optional flashlight uses Android torch APIs.
- The GitHub repository is public and includes an Apache-2.0 license. R8 protects only the distributed APK from casual inspection; it does not hide source code already published in Git history or revoke rights already granted by Apache-2.0.

## Implementation phases

### Phase 1 — Repository and supply-chain controls
- Keep GitHub Actions secrets out of source, logs and artifacts.
- Keep secret scanning, push protection, Dependabot alerts and dependency updates enabled.
- Review branch protection, required CI checks, least-privilege workflow permissions and dependency pinning.
- Decide separately whether to retain the public Apache-2.0 source model or create a private source repository. Do not silently change visibility or licensing: existing public copies and Apache-2.0 grants cannot be recalled, and a private repository changes how contributors and users access source/releases.

### Phase 2 — APK hardening
- R8 minification, code shrinking and resource shrinking enabled for release builds on this branch.
- Keep debug builds readable for diagnostics.
- Keep the R8 mapping file private; never attach it to public releases.
- Add narrowly scoped keep rules only when reflection/serialization requirements or failing tests prove they are necessary.
- Inspect APK contents and run the complete regression suite against the minified APK.

### Phase 3 — Local data protection
- Audit every preference, file, exported event and user-selected URI.
- Identify sensitive data and minimize retention first.
- Evaluate Android Keystore-backed encryption for sensitive local records.
- Preserve old data with a crash-safe migration; never make encrypted storage a prerequisite that can erase or strand an active alarm.
- Keep device credentials and biometric templates inside Android system APIs; never attempt to collect them.

### Phase 4 — Update channel hardening
- Preserve the existing package ID and permanent signer.
- Verify HTTPS origin, package identity, version monotonicity, SHA-256 and signer certificate before installer handoff.
- Reject corrupted, mismatched, unsigned or wrongly signed packages.
- Test update interruption, retry, insufficient storage, stale metadata and downgrade attempts.
- Do not embed GitHub tokens, signing passwords or private keys in the APK.

### Phase 5 — Tamper and runtime resilience
- Add proportionate integrity signals only where they do not block legitimate owner devices.
- Treat root/debugger/tamper indicators as risk signals, not proof of malicious use.
- Never use invasive permissions, Accessibility abuse, overlays to intercept credentials, root exploits or hidden persistence.
- Preserve Android/OEM compatibility and offline alarm operation.

### Phase 6 — Verification and release gate
- Run unit tests, lint, minified release build and APK package/version/signer/checksum verification.
- Test upgrade-over-install from v1.1.3 with settings and data preservation.
- Repeat the owner's 11 physical scenarios on the hardened build and record results.
- Test supported Android/OEM combinations where devices are available.
- Do not tag or publish v1.1.4 until the owner has finished feature additions and explicitly approves release.
